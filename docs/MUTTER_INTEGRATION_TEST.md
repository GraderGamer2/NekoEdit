# GNOME Shell / Mutter integration smoke test

This test exercises NekoEdit through GNOME Shell 46 / Mutter's native Wayland backend, not only the repository's protocol mock. GNOME Shell, Mutter, the native virtual-input session, and the test extension are test-only; the editor remains freestanding and does not link GNOME, GTK, Mutter, libwayland, X11, or an input automation library.

## What it covers

Before the live compositor test, CI runs `make test-xkb-native`. That host-side test asks libxkbcommon to compile the same `evdev` / `pc105` / `us(intl)` / `compose:ralt` keymap, passes its generated XKB text through NekoEdit's assembly parser, and verifies that `Multi_key`, `dead_grave`, and `dead_circumflex` survive parsing at the same keycode/group/level positions. `libxkbcommon-dev` is a CI test dependency only; it is not linked into NekoEdit.

The test starts GNOME Shell with Mutter's native `--headless` backend and a `1280x720` virtual monitor. This avoids the nested-X11 input path, where XTEST events are not accepted as physical input by Mutter's Wayland seat. The temporary GNOME keyfile configures `org.gnome.desktop.input-sources` to use `us(intl)`, `compose:ralt`, and `pc105`; the harness reads back and verifies these settings before Shell starts. `XKB_DEFAULT_*` environment variables alone do not configure Mutter's native seat, which starts with a plain `us` map. Only after the keymap is applied does the harness launch the normal NekoEdit executable against the compositor's private Wayland socket with a temporary HOME and a separately installed `pt_BR.UTF-8` NLP1 pack.

A small GNOME Shell extension is copied into that temporary HOME and enabled through an isolated GLib keyfile GSettings backend. The extension reports the actual focused Mutter `MetaWindow` by process ID, creates a session using Mutter's `org.gnome.Mutter.RemoteDesktop` D-Bus API, and uses its native pointer-notification methods to move into and click the editor's document body before typing. It calls `CreateSession` and `Start` through the same GNOME Shell D-Bus connection, which is required by Mutter's same-peer session permission check. The harness sends and releases Ctrl_L before launching NekoEdit: Mutter creates the native virtual keyboard lazily on the first `NotifyKeyboardKeysym` press, and this primes the `wl_seat` keyboard capability before the editor binds the seat. The extension then activates NekoEdit and sends the actual test sequence through the native input seat; no XTEST device or host X window is involved.

The harness first activates NekoEdit by PID, then sends a native pointer move and left-button click at the center of the document body. It then sends Ctrl+A and `x`, followed by Ctrl+S and Enter. Save confirmation is enabled by default in NekoEdit, so Enter explicitly accepts the confirmation modal; without it, Ctrl+S intentionally leaves the file unchanged. The harness checks that the saved document contains exactly `x`. Only after that canary succeeds does it test:

1. Right Alt (`compose:ralt`) as `Multi_key`, period, period, producing U+2026 (…).
2. Under the verified `us(intl)` keymap, the grave key (`dead_grave`), Shift+6 (`dead_circumflex`), and Shift+A, which must resolve through the separate `pt_BR.UTF-8` locale pack to U+1EA6 (Ầ).
3. Ctrl+S and Enter to accept the default save-confirmation modal, followed by an exact UTF-8 byte comparison against `…Ầ`.

Build and test [#833](https://github.com/GraderGamer2/NekoEdit/actions/runs/43103083452) completed this full sequence successfully on Ubuntu 24.04 with GNOME Shell 46 / Mutter 46.2. The log shows the compositor actually advertised text-input-v3, so the live manager/enter/enable/state-commit branch was exercised rather than only the no-global fallback.

After that Compose test, the first editor process is closed and a second instance is launched with `NEKOEDIT_ENABLE_TEXT_INPUT=1`. The Python probe is the direct parent of this second process; using `nm` symbol addresses and read-only `/proc/<pid>/mem`, it observes the client state without adding debug hooks to the application. It also activates the real Mutter window and clicks the document area. If Mutter advertises `zwp_text_input_manager_v3`, the probe requires a successful manager bind, a text-input `enter`, document `enable`, and at least one committed state update. If the compositor does not advertise the global, it requires all text-input objects to remain inactive and verifies that ordinary physical-keyboard/XKB typing and the confirmed save path still work with the opt-in environment variable set. The branch is selected from the actual registry result, not from a compositor-version assumption.

## Live IBus Simple phase

Before GNOME Shell starts, the headless harness updates the D-Bus activation environment with its temporary `HOME`, XDG paths, session type, and Wayland display. It starts the GNOME-mode IBus daemon on the private `dbus-run-session` bus and verifies that `org.freedesktop.IBus` has an owner. It then reads the daemon's actual IBus socket address with `ibus address`, exports it as `IBUS_ADDRESS`, and updates the D-Bus activation environment again. This is essential because IBus clients prefer `IBUS_ADDRESS` and otherwise discover the socket under the user's config directory, while D-Bus-activated services inherit the bus daemon's activation environment rather than the harness's later shell exports. The harness explicitly activates `org.freedesktop.portal.IBus` and requires the portal to own its session-bus name before GNOME Shell starts. The harness runs Mutter/GNOME Shell directly rather than a complete `gnome-session` with a systemd user manager; the normal GNOME IBus unit is therefore not used. After the original physical-XKB/Compose canary completes, the harness changes only the temporary GNOME input-source settings to `('ibus', 'xkb:us:intl:eng')`. This is IBus Simple's XKB-backed engine for the same `us(intl)` layout, and the test waits for `ibus engine` to report that exact engine as active.

The second NekoEdit process receives the explicit `NEKOEDIT_ENABLE_TEXT_INPUT=1` opt-in. The test extension exposes both Mutter RemoteDesktop keyboard injection methods: `NotifyKeyboardKeysym` for logical shortcut keys and `NotifyKeyboardKeycode` for raw evdev input. For the IBus preedit canary it sends Linux evdev `KEY_APOSTROPHE=40`, `KEY_BACKSPACE=14`, then `KEY_APOSTROPHE=40` and `KEY_E=18`. The harness does not inspect `global.stage` for these keystrokes: NekoEdit is a separate Wayland client, and keys consumed by the compositor's input method are not reliably observable through a stage-level capture callback. Instead, the temporary Shell extension queries the actual `Clutter.InputMethod` instance installed on GNOME Shell's Clutter backend. Its test-only D-Bus status reports the current input source, IBus context availability, input-method focus, and provider preedit visibility/text. It also wraps the Shell input method's existing `process_key_event_async` method on that IBus context instance, records the keyval/keycode/modifier arguments, then calls the original method unchanged with the original callback and remaining arguments. The probe requires the active source to be `ibus:xkb:us:intl:eng` and a ready, focused IBus context. Because Shell's `xkb:` engines echo the compositor's translated keysyms, the harness reapplies the exact `us(intl)` keymap after switching sources and requires the physical apostrophe to arrive at the IBus call boundary as `dead_acute` (keysym `0xfe51`, evdev keycode 40), not an ordinary apostrophe. If Shell reports provider preedit but NekoEdit does not apply it, the parent-side probe also reads the last staged Wayland preedit payload—including UTF-8 text and both cursor offsets—before the parser's boundary validation. This establishes whether Mutter's wire-format offsets are what caused the client to reject the event. The CI's Mutter 46.2 package demonstrated the historical anchor-offset bug: for `´` it sent byte cursor 2 and character anchor 1. NekoEdit handles only this collapsed-caret legacy form by converting the anchor from scalar index to byte offset when—and only when—it resolves to the same already-validated cursor. Other malformed offsets and non-collapsed ranges continue to be rejected. Mutter fixed the upstream bug in [f214eb5](https://github.com/GNOME/mutter/commit/f214eb513429b9434d88dd4fce115aef8ab977bc); the corrected conversion is present in Mutter 46.3. This distinguishes a key-routing problem from a provider/input-source problem and from a failure to deliver or apply the Wayland preedit event. The existing parent-owned `/proc/<pid>/mem` inspection still requires a non-empty provider preedit while the document remains empty, Backspace to cancel without committing text, then a fresh apostrophe followed by `e` to commit U+00E9 LATIN SMALL LETTER E WITH ACUTE (UTF-8 `C3 A9`). It also verifies that both Shell and client preedit clear and that the exact bytes survive the normal Ctrl+S / Enter save-confirmation flow. The first, separate Mutter phase continues to test the physical-XKB `Multi_key` Compose mapping. The IBus phase intentionally does not depend on IBus 1.5.29 inheriting the compositor's Compose-key XKB option on Wayland (see [IBus issue #2579](https://github.com/ibus/ibus/issues/2579)).

This is intended as a real IBus engine-to-GNOME-Shell-to-Mutter-to-NekoEdit integration test, not a mock IBus signal. The live probe also records the last Wayland object/opcode/size, staged preedit payload, pending-preedit flags/offsets, active preedit offsets, and Shell's state after Backspace. This distinguishes a missing clear event, an invalid clear payload, and a clear event that is staged but not applied. The Shell extension additionally wraps the active Clutter.InputMethod `set_preedit_text` API and records each call's text, cursor, anchor, and reset mode while forwarding the original arguments and receiver unchanged. That isolates whether GNOME Shell actually asks Mutter to clear the client preedit before checking the Wayland side. The CI trace confirmed GNOME Shell calls `set_preedit_text(NULL, 1, 1)`; Mutter 46.2 forwards it as a NULL text-input string with byte offsets `(0, 1)`, which NekoEdit rejects because an empty string has only boundary `0`. NekoEdit now repairs only that precise nullable-empty legacy pattern to `(0, 0)`, and the Wayland mock verifies the previous composition is cleared. The `ibus` command, IBus daemon, IBus Simple engine, `dbus-update-activation-environment` utility, and the test-only Clutter.InputMethod state query are test-session dependencies only. The harness supervises the daemon and updates D-Bus's activation environment so the portal receives the isolated HOME/XDG paths and IBus socket address. NekoEdit still links no IBus, D-Bus, GNOME, or other runtime library. Provider-originated delete-surrounding remains a deterministic Wayland-mock case, and Fcitx/other engines still need separate validation.

The extension, remote-desktop session, GSettings keyfile, editor preferences, locale pack, Wayland runtime directory, and temporary monitor are all limited to the test process and its temporary HOME. The one pre-launch Ctrl_L press is released before NekoEdit is started and exists only to instantiate the virtual keyboard device. GNOME Shell applies `us(intl)` and `compose:ralt` to Mutter's actual backend keymap before NekoEdit connects, so the tested keysyms correspond to keys that exist in that map. No remote-desktop daemon, network listener, RDP port, or user desktop session is configured.

## Run it

On Ubuntu 24.04:

    sudo apt-get update
    sudo apt-get install --no-install-recommends gnome-shell ibus dbus-daemon libglib2.0-bin libxkbcommon-dev
    make clean all
    make test-xkb-native
    make test-mutter

The Make target builds optional locale packs separately and launches the harness under `dbus-run-session`. The headless compositor publishes a private Wayland socket under the test's temporary `XDG_RUNTIME_DIR`; NekoEdit connects to that socket exactly as it would to a normal Wayland compositor.

## Validation boundary

This is real GNOME Shell/Mutter native Wayland seat coverage with a native virtual input device. It validates Wayland pointer focus, key delivery, shortcuts, `Multi_key`, locale-specific dead-key composition, the default save-confirmation interaction, and the text-input-v3 client activation boundary. When the compositor exports the manager, the probe verifies client-side bind/focus/enable/state-commit; when it does not, the probe verifies graceful opt-in fallback to physical XKB typing. The live IBus Simple dead-key preedit/commit scenario is under validation and is not yet a passing CI assertion. Provider-originated delete-surrounding, Fcitx, other third-party engines, physical keyboard hardware, other desktop environments, and complex-script shaping remain separate checks.

The temporary extension exports only readiness, focus-by-PID, and narrowly scoped remote-keyboard operations on the private CI D-Bus session. It does not enable GNOME Shell's arbitrary Eval interface. The extension and all temporary data are removed after success; none becomes an editor runtime dependency. Ordinary `make test` and `make test-wayland` remain usable without GNOME Shell.
