# Wayland backend: interactive editing prototype

## Purpose and current scope

This document describes the current native Wayland development slice. It is deliberately not a complete Wayland client implementation. The freestanding x86-64 assembly program creates a software-rendered toplevel without GTK, Qt, libwayland, libc, or another third-party runtime library. It supports physical XKB text-v1 input (including explicit Unicode keysyms, 273 curated named non-ASCII aliases, a bounded 40-pair `Multi_key` table, and six dead-key actions) plus optional compositor-provided `zwp_text_input_v3` preedit/commit input. Both paths feed grapheme-aware editing of valid UTF-8 documents; text-input-v3 is bound only when `NEKOEDIT_ENABLE_TEXT_INPUT=1` is explicitly set and the compositor later grants text focus.

The prototype currently:

- Uses WAYLAND_SOCKET when a launcher supplies an inherited, already-connected socket descriptor. Otherwise connects to WAYLAND_DISPLAY (defaulting to wayland-0 under XDG_RUNTIME_DIR); an absolute WAYLAND_DISPLAY path is also accepted.
- Discovers and binds wl_compositor, wl_shm, and xdg_wm_base; an optional wl_seat is bound after the initial window objects.
- Creates one top-level window with the title “NekoEdit - development window”. The software-rendered UI shows a compact application title bar, app-drawn Minimize, Maximize/Restore, and Close controls, an active document tab, an editor area, and a live status bar.
- Starts at 800×480 and advertises a 480×360 minimum and 3840×2160 maximum geometry through `xdg_toplevel.set_min_size`/`set_max_size`. Positive compositor configure dimensions are used exactly within that shared-memory limit rather than silently clamped; rectangle and glyph writes are clipped to the active surface.
- Passes the backing memfd to the compositor with SCM_RIGHTS.
- Handles the initial xdg configure/acknowledge handshake.
- Binds wl_seat when advertised, creates wl_pointer and wl_keyboard after the seat reports the corresponding capabilities, and handles pointer enter, leave, motion, and button events plus keyboard focus, key, and modifier events. Button serials are retained for compositor-mediated interactive window move/resize requests.
- Provides a compact title bar, an Untitled document tab, a document area, and a live status bar. Pointer clicks place the caret at the nearest insertion boundary; single-click dragging selects byte ranges across lines and visual rows. Double-click selects a complete word and retains the pointer grab so a continued drag extends or reverses the selection by whole words. Drags outside the document/window continue to update selection; a separate timer performs vertical edge auto-scroll in both wrap modes and horizontal edge auto-scroll when wrapping is disabled, including while the pointer is stationary. Valid UTF-8 uses Unicode 18.0 extended grapheme boundaries for navigation, hit-testing, selection, Backspace, and Delete, while malformed bytes remain individually editable. Focused document typing uses the supported XKB text-v1 subset, including explicit Unicode keysym forms, named non-ASCII aliases, the bounded 40-pair two-symbol `Multi_key` Compose path, and the six-accent dead-key path, with a US-QWERTY fallback; prompt and search-field input remains in the ASCII subset. The editor implements Ctrl+A, Ctrl+C, Ctrl+X, Ctrl+V, Ctrl+Z, Ctrl+Y, Ctrl+Shift+Z, Ctrl+O, Ctrl+S, and Ctrl+Shift+S, along with typing, Enter, Tab, Backspace/Delete and navigation.
- Uses an mmap-backed gap buffer that grows geometrically from 64 KiB up to 1 GiB and a per-line byte-span/visual-row index backed by Fenwick prefix trees. The software renderer uses supported TrueType fonts when available, with the embedded 5×7 bitmap as fallback; glyph advances and line pitch come from parsed font metrics. The XKB parser extracts common ASCII keysyms, explicit Unicode Uxxxx/Uxxxxx/Uxxxxxx scalars, 273 curated named non-ASCII aliases (including Latin-1, Greek, Cyrillic, common regional variants, EuroSign, and punctuation), the `Multi_key` action token, and six reserved dead-key actions into parallel lookup tables. It parses up to 64 declared `xkb_types` entries, 32 exact modifier-to-level map entries per type, four symbol groups and eight levels per group, and up to 24 virtual-modifier declarations. Per-key `type[GroupN]` assignments are retained. Explicit `virtual_modifiers NAME = ...` encodings are parsed as real-modifier combinations, numeric masks, or `none`; declaration indices are kept separate from the effective 32-bit masks sent by Wayland. The fixture verifies `LevelThree = Mod5`, `NumLock = Mod2`, a combined real-modifier mask, a mask at bit 31, duplicate declarations across keymap components, and repeat policy precedence for a default-false compatibility section, a repeat-true interpretation, and direct per-key false/true settings. The keyboard integration scenario also holds each synthetic key through the actual Wayland event path: false policies must not start a timer, while compatibility-true and direct-true policies must repeat using the compositor-provided delay/rate. At lookup, the compositor's 32-bit XKB state is filtered through the selected type's declared `modifiers` mask and compared exactly with its `map[]` entries; numeric masks and numeric/`LevelN` level values are supported.
- Keeps a single active `wl_buffer` release-safe and requests one `wl_surface.frame` callback for each non-initial redraw. Subsequent visual changes are coalesced in `redraw_pending`; the next commit is submitted only after both `wl_buffer.release` and `wl_callback.done` have arrived, regardless of event order. Resizing still waits for buffer release before destroying or replacing its storage.
- Sends `xdg_toplevel.move` from blank title-bar drags and `xdg_toplevel.resize` from a 12-pixel edge/corner hit region, using the serial from the initiating `wl_pointer.button` press.
- Maximize/Restore/Minimize requests return to the event loop without a stale-size surface commit. The next frame follows the compositor's toplevel/surface configure and `ack_configure` sequence; if the old buffer is still busy, replacement waits for `wl_buffer.release`.
- Answers xdg_wm_base ping requests.
- Sends Wayland socket requests with `MSG_NOSIGNAL`, so a closed compositor connection is returned as an ordinary write error instead of terminating the process with SIGPIPE. Failed sends report the client object ID, opcode, and Linux errno on stderr; this requires no journal or logfile. They also report the last complete client request written to the socket and the last Wayland event read, including its payload length. These are sequence clues, not proof that the compositor processed the preceding request.
- Exits on xdg_toplevel.close.

The wl_keyboard.keymap FD is received with recvmsg/SCM_RIGHTS, validated as a bounded NUL-terminated xkb_v1 keymap, and mapped read-only with MAP_PRIVATE. The parser supports compiled keycodes and aliases, common ASCII keysyms, explicit Unicode Uxxxx/Uxxxxx/Uxxxxxx keysyms, 273 curated named non-ASCII aliases, four symbol groups with up to eight levels each, and declared per-key types. Unicode scalars are stored in a parallel per-key/group/level table; document typing converts valid scalars to UTF-8. It supports up to 64 key types, 32 map entries per type, exact modifier filtering, and explicit virtual-modifier encodings from real modifier names, numeric masks, or `none`. Declaration indices remain separate from the effective masks. Unsupported maps fall back to US-QWERTY. Direct key `virtualModifiers` properties and direct keycode `modifier_map` entries are parsed; the corresponding real modifier masks are ORed into the explicit virtual-modifier encoding. Aliases outside the curated 273-name table, unrecognized indirect keysym-based `modifier_map` lookup, general XKB `xkb_compat` interpretation/action resolution beyond the bounded virtualModifier/useModMapMods/repeat subset, and full Compose data are not implemented. Type `preserve[]` masks are supported for the selected exact map entry; the key-specific consumed mask filters both Control and Shift from shortcut dispatch when consumed, while preserved modifiers remain available. Alt is not currently used by the implemented shortcut set and is not filtered there. The compositor remains responsible for applying stateful keymap actions and delivering the resulting 32-bit XKB state. Six dead-key names (grave, acute, circumflex, tilde, diaeresis, cedilla) are recognized; 52 common Latin-1 pairs compose to precomposed characters, and unsupported pairs insert base+combining-mark. The `Multi_key` action implements a separate bounded table of 40 two-symbol pairs; unsupported pairs are inserted literally, and Escape/Backspace cancel an incomplete sequence. Longer/multi-stage or locale-provided Compose tables remain unsupported. Basic Wayland text-input-v3 preedit/commit/delete handling is implemented; richer preedit attributes, full shaping, and live compositor validation remain incomplete. The document uses Unicode 18.0 extended grapheme segmentation, a geometrically growing gap buffer, an indexed logical-line/Fenwick layout, proportional TrueType advances, font-metric line pitch, and vertical/horizontal scrolling. The Wayland data-device backend implements immutable-snapshot Ctrl+C/X and asynchronous Ctrl+V. The optional Clipboard Service forks a small helper on window close to keep the current selection available through the original Wayland client connection. Ctrl+Z/Y and Ctrl+Shift+Z use a per-document disk-backed delta journal; the History tab provides Undo/Redo counts, Export, and Delete. Asynchronous external paste is wrapped as one history transaction. Settings exposes independently adjustable document (8–32px) and UI (8–16px) font sizes, with the dropdown remaining open during repeated adjustments. Document/UI sizes, Wrap Lines, Confirm before saving, and the selected TTF path persist in `~/.nekoedit/preferences`. Settings and Find/Replace panels retain fixed centered dimensions while their text follows the selected UI font. Find highlights every literal query match, with the current selection visually distinct. Still unsupported: general XKB compatibility/action interpretation beyond the implemented virtualModifier/useModMapMods/repeat subset, implicit modifier bindings outside the bounded recognized-key set, preserve/consumed-modifier semantics, aliases outside the curated named-symbol table, longer and locale-specific Compose sequences beyond the bounded 40-pair `Multi_key` table and six-dead-key Latin-1 subset, advanced text-input-v3 preedit attributes/cursor styling, complex shaping/kerning/mark positioning, font-family discovery beyond the picker, fractional/output scaling, a release-tracked multi-buffer set, and X11. Single-buffer wl_surface.frame pacing is implemented; the client still uses one active wl_buffer and gates its next ordinary redraw on both release and callback completion.

## Protocol flow

The implementation sends and receives the Wayland protocol directly over an AF_UNIX/SOCK_STREAM socket. The current binding version is 1 for each interface.

1. Resolve the connection: use the decimal file descriptor in WAYLAND_SOCKET when present; otherwise create and connect an AF_UNIX socket using WAYLAND_DISPLAY and XDG_RUNTIME_DIR.
2. Send wl_display.get_registry and wl_display.sync.
2. Process wl_registry.global events and remember the registry names for wl_compositor, wl_shm, and xdg_wm_base.
3. Bind those globals to client object IDs 4, 5, and 6.
4. Allocate subsequent client object IDs densely: the second sync callback is ID 7, wl_surface 8, xdg_surface 9, xdg_toplevel 10, and wl_shm_pool 11. The initial `wl_buffer` is ID 12; resize-created buffers receive monotonically increasing IDs beginning at 256. If `wl_seat` is advertised, it is bound as object 13, a sync callback uses object 14, and `wl_pointer` is object 15 when pointer capability is present. Skipped IDs are a protocol error on strict compositors.
5. Send a second wl_display.sync to ensure the bindings have been processed.
6. Create a wl_surface using wl_compositor.
7. Create its xdg_surface role and xdg_toplevel using xdg_wm_base; advertise the minimum and maximum supported window geometry with xdg_toplevel.set_min_size/set_max_size.
8. Set the toplevel title and issue an initial empty wl_surface.commit.
9. Wait for xdg_surface.configure and send xdg_surface.ack_configure with its serial.
10. Call memfd_create, ftruncate, and mmap to create a shared pixel buffer.
11. Send wl_shm.create_pool with the memfd attached as SCM_RIGHTS ancillary data.
12. Create the initial wl_buffer from the pool, attach it, damage the surface, and commit. Keep the wl_shm_pool alive: later configure events can allocate size-specific buffers from the same bounded mapping.

The initial surface commit is required to receive the first configure. The buffer is attached only after acknowledging that configure.

## Seat capability hotplug

The backend treats each `wl_seat.capabilities` event as the complete current capability mask. When pointer capability disappears, it clears pointer focus/serial and button/scroll drag state, stops pointer-selection auto-scroll, destroys the pointer-bound cursor-shape device, and drops the old `wl_pointer` proxy. When keyboard capability disappears, it cancels repeat, clears held modifier/lock state and pending dead-key/Compose sequences, drops the old `wl_keyboard` proxy, and disables text-input-v3 so transient preedit is cleared. If that transition leaves the surface dirty while the shared-buffer and frame-callback gates are idle, the event handler submits the redraw immediately; otherwise the ordinary release/callback completion path flushes it. Reappearing capabilities receive fresh client object IDs; the cursor-shape manager remains bound, while its device is recreated for the replacement pointer.

The seat is bound at no more than version 4. For versions 3–4, pointer and keyboard removal sends their protocol `release` requests before dropping the proxies. Versions 1–2 do not define those release requests, so the client only abandons the local proxies and never sends unsupported opcodes. It still creates fresh object IDs on re-addition. The mock covers both paths and verifies that the replacement cursor-shape device refers to the new pointer and uses its new enter serial, and that keyboard focus/modifiers are cleared on removal.

## Keyboard hotplug during active IME composition

The Wayland mock also covers an opted-in text-input-v3 session with a visible, uncommitted preedit string when wl_seat.capabilities removes the keyboard. The client must send the text-input disable request followed by commit, clear the transient preedit cursor/text, keep the document bytes unchanged, and repaint immediately when the shared-buffer and frame-callback gates are idle. This is a protocol-level regression test; the regular default-off behavior and live Mutter/IBus probe remain separate checks.

## Logical surface and backing-buffer geometry

`window_width` and `window_height` remain surface-local logical dimensions. They are used for `xdg_toplevel.configure`, application layout, pointer hit-testing, text metrics, IME cursor rectangles, and the `wl_surface.damage` rectangle. The backing store has separate `window_buffer_width` and `window_buffer_height` pixel extents plus a physical byte pitch in `window_stride`.

`window_buffer_scale` currently supports integer 1× and 2×. The client prefers `wl_surface.preferred_buffer_scale` on `wl_compositor` v6 and newer; older compositors use the maximum committed scale among outputs entered by the surface. The actual scale is capped at 2× and is reduced to 1× whenever the logical surface exceeds 1920×1080, keeping every buffer within the existing 3840×2160, four-byte-per-pixel shared-memory pool. Compositors below `wl_compositor` v3 use 1× because `wl_surface.set_buffer_scale` is not available there.

All raster output crosses the logical-to-physical boundary after layout transforms: filled rectangles, TrueType glyph origins and em sizes, and the embedded 5×7 fallback are rendered at the selected physical scale. Text advances, wrap/index calculations, caret and pointer hit-testing, editor layout, and IME rectangles remain logical; they are not multiplied before hit-testing. The client sends `wl_surface.set_buffer_scale` only when the desired scale differs from the current surface state, in the same commit as the matching buffer attachment. `wl_surface.damage` continues to use surface-local coordinates rather than buffer pixels.

A scale-only change is treated as a buffer replacement even when logical window dimensions are unchanged. If the single active buffer is still owned by the compositor, the new scale is pending until `wl_buffer.release`; startup also replaces an unattached initial buffer when a preference arrives during the initial seat roundtrip. The Wayland mock checks a 2× first frame and 1×→2×→1× runtime changes, including physical dimensions/stride, rendered pixel coverage, logical damage rectangles, and release-gated replacement. Scale-2 backing dimensions never exceed the preallocated shared-memory capacity.

Preferred buffer transforms are still tracked but not applied; 90°/270° axis swaps and reflections remain future work. Fractional scaling via `wp_fractional_scale_v1`/`wp_viewporter` and a release-tracked multi-buffer set are also not implemented.

## Output discovery and integer-scale metadata

The client discovers up to eight `wl_output` globals and binds each at no more than protocol version 3. Binding is deferred until the fixed surface/toplevel/shared-memory and seat bootstrap objects, plus any optional pointer/clipboard/text-input proxies, have been assigned contiguous client object IDs. The initial buffer is attached only after those output bindings, so a real compositor never sees an invalid client-side new ID that skips over unallocated object IDs. Each cache entry retains the registry global name, bound client object ID, negotiated version, committed integer scale (default 1), pending scale, and whether the application surface has entered that output. A v2+ `wl_output.scale` event stages a positive integer; the value becomes visible to the cache only on the matching `wl_output.done`. The backend also handles `wl_surface.enter/leave` and `wl_registry.global_remove`. It sends `wl_output.release` only for v3 resources, which define that request; v1/v2 resources are abandoned locally without an unsupported opcode. Newly announced outputs use a free cache slot and a fresh client object ID from the shared monotonic allocator.

The backend maintains the number of outputs currently containing the surface and the maximum committed integer scale among them (returning to 1 when none are entered). It derives the effective scale hint from the maximum committed entered-output scale on `wl_compositor` versions 1–5 and from `wl_surface.preferred_buffer_scale` on version 6+, including the protocol default of 1 before the first preference event. NekoEdit converts that hint into an applied raster scale of 1× or 2×, subject to the shared-memory geometry cap described above. The mock exercises both compositor-version paths, including atomic `wl_output.done` updates, surface enter/leave, hotplug, and the v6 preferred-scale path. Output scale now affects backing-buffer dimensions and software rasterization while logical layout/input coordinates remain unchanged. Fractional scale and preferred buffer transforms are not yet applied.

## Preferred buffer scale and transform

When the compositor advertises `wl_compositor` version 6 or newer, NekoEdit binds it at version 6 and the created `wl_surface` can receive `preferred_buffer_scale` and `preferred_buffer_transform`. The client tracks both per-surface preferences, validates positive scale values and the transform enum, and applies the preferred scale through the bounded 1×/2× raster path. Older compositors retain the default surface preference and derive the scale hint from committed `wl_output.scale` values for outputs entered by the surface.

For v6+, the per-surface preference is authoritative; the output maximum remains fallback/diagnostic metadata. The protocol default is 1 before the first preference event, and the core protocol directs clients to prefer the per-surface event over `wl_output.scale` ([core protocol](https://wayland.app/protocols/wayland#wl_surface)). The selected scale is applied to buffer geometry and raster output, but not to logical layout or input coordinates. The preferred transform remains metadata-only in this milestone: NekoEdit does not yet set a non-normal `wl_surface` buffer transform or rotate/reflect the software raster.

## XKB compatibility modifier-map scope

The bounded `xkb_compat` reader supports both `useModMapMods = level1` and `useModMapMods = any`. When the attribute is omitted, XKB's default is `any`. The `level1` scope considers the keysym at Group 1 / Level 1; `any` considers occurrences in any group and level. When multiple matching interpretations have equal specificity, the first declaration wins.

The Wayland mock places the same `ISO_Level3_Shift` keysym on Group 1 / Level 1, Group 1 / Level 2, and Group 2 / Level 1. It verifies that an earlier `level1` interpretation handles the first occurrence and a later `any` interpretation handles the other two. A separate Group 2-only `ISO_Group_Shift` key omits the attribute and verifies the implicit `any` default. The tests also inspect the resulting real/virtual modifier aggregation.

This is bounded compatibility interpretation coverage, not general XKB action execution. Stateful modifier/group actions remain compositor-owned.

## XKB per-key repeat and compositor-owned key actions

The keymap reader keeps direct `repeat = True/False` declarations in `xkb_symbols` separate from `xkb_compat` interpretation policy. The compatibility-section `interpret.repeat` default is `False`, and an interpretation may override it with its own `repeat` field. When no compatibility interpretation matches, XKB's default interpretation enables repeat only if the key has a Group 1 / Level 1 symbol; a key without that base-level symbol retains the ordinary non-repeat default. Because repeat is key-wide, both compatibility matching and the fallback are evaluated only from Group 1 / Level 1. An explicit key-level `repeat` property takes precedence over either compatibility result.

On a physical key-down event, the Wayland backend queries this per-key policy before starting its existing timer. The compositor's `wl_keyboard.repeat_info` rate and delay still determine the timing; the keymap determines whether that particular key may repeat. A mapped key with a Group 1 / Level 1 symbol and no matching compatibility interpretation inherits the default-interpret repeat behavior; a mapped key without that base symbol does not repeat unless its key declaration explicitly enables it. Keycodes absent from the loaded map are non-repeatable.

NekoEdit does not execute stateful XKB modifier/group actions such as `SetMods` or `SetGroup` in the Wayland client. The compositor interprets those actions and reports the resulting depressed/latched/locked modifier masks and group through `wl_keyboard.modifiers`; the client consumes that state for symbol lookup. This avoids applying the same modifier/group transition twice.

## Text input and IME (optional text-input-v3)

The client discovers `zwp_text_input_manager_v3` as an optional registry global, but binds version 1 and creates a `zwp_text_input_v3` object only when `NEKOEDIT_ENABLE_TEXT_INPUT=1` is present in the process environment. The default is deliberately OFF: the text-input-v3 path suppresses printable `wl_keyboard` insertion while it waits for IME commits, and that handoff has not yet been verified on the user's live GNOME/Mutter desktop. Therefore, an advertised manager alone never steals ordinary typing; the physical XKB path remains active by default. To test the current IME implementation, launch with `NEKOEDIT_ENABLE_TEXT_INPUT=1 ./nekoedit --backend=wayland`. This switch is not persisted in `~/.nekoedit/preferences`.

When opted in, text input is enabled only after the text-input object enters this surface and the document is the active input target. The client disables it when the surface leaves the input-method target or focus moves to the file picker, path prompt, Find/Replace, save confirmation, or History page. While text-input-v3 is enabled, printable physical-key insertion is suppressed to avoid inserting a key twice; navigation and editor shortcuts continue through `wl_keyboard`.

For each state update, the client sends:
- `set_content_type` with normal-purpose/default hints;
- a bounded surrounding-text window of at most 4000 bytes, aligned to valid UTF-8 scalar boundaries, plus byte offsets for the caret and selection anchor;
- a surface-local `set_cursor_rectangle` based on the document caret;
- `commit`, with a monotonically advanced client commit serial.

The event handler stages `preedit_string`, `commit_string`, and `delete_surrounding_text` until `done`. A preedit candidate is copied into a separate staging area, UTF-8 validated, and accepted only when both cursor offsets are valid UTF-8 byte boundaries within the string; a rejected event leaves the previous valid preedit candidate untouched. The offsets are byte indices, not Unicode-scalar or grapheme counts. A pair of `-1` offsets hides the preedit cursor; otherwise the renderer orders the begin/end interval for highlighting while positioning the IME cursor at `cursor_begin`. Committed strings are UTF-8 validated before insertion. Delete ranges are checked for document bounds and UTF-8 boundaries; invalid ranges are ignored. A delete-plus-commit update is recorded as one history action. Preedit remains transient: it is drawn as an underlined overlay with a selected-range highlight and is not written to the document or journal until committed. Serial mismatches do not trigger a repeated state-commit loop; the client waits for a matching `done` before resynchronizing its surrounding-text/cursor state.

Current limits: text-input-v3 supplies the preedit cursor and selected range, not arbitrary styled attribute runs; NekoEdit renders an underline and a simple range highlight. Candidate-window positioning follows the preedit caret calculated with the current glyph advances, and the preedit renderer remains unshaped. Complex-script shaping, combining-mark placement, bidirectional layout, and locale-specific composition still belong to the later text-layout milestone.

The protocol implementation is checked against a mock compositor for manager binding, enter/leave, enable/disable, surrounding text, serial stability, preedit staging, multibyte UTF-8 commit, valid/invalid surrounding deletion, and redraw sequencing. This is protocol-level automation, not a live GNOME/Mutter or real input-method test. The protocol definition is maintained in [wayland-protocols](https://gitlab.freedesktop.org/wayland/wayland-protocols/-/blob/main/unstable/text-input/text-input-unstable-v3.xml).

## Shared-memory buffer

The initial surface is 800×480 with a 3200-byte stride and WL_SHM_FORMAT_XRGB8888. The memfd mapping is reserved for the maximum 3840×2160 surface (four bytes per pixel); each created wl_buffer uses the active width, height, and stride. The buffer is drawn entirely by CPU stores:

- Full background: 0xFF252A33.
- Header band: 0xFF343D4B.
- Small accent mark: 0xFF78A9D4.

The memfd is sized before mapping. The request uses sendmsg with a SOL_SOCKET/SCM_RIGHTS control message to transfer the descriptor to the compositor. The renderer still has one active wl_buffer, and it never writes to that storage while the compositor owns it. Each normal redraw requests `wl_surface.frame`; `redraw_pending` coalesces intervening changes until both the callback's `done` event and `wl_buffer.release` have arrived. The event loop handles either completion order. This paces submissions but does not eliminate single-buffer stalls; a small release-tracked multi-buffer set remains future work.

## Event handling

The event loop uses `poll()` for the Wayland socket, key-repeat timer, four nonblocking clipboard-send descriptors, and one clipboard-receive descriptor. An interrupted `poll()` (`EINTR`) restarts the event-loop iteration; a signal interrupt is not treated as a Wayland protocol failure. Keyboard shortcuts include Ctrl+O/S/Shift+S, Ctrl+C/X/V, Ctrl+Z/Y and Ctrl+Shift+Z. Clipboard transfers use bounded nonblocking chunks, without blocking keyboard dispatch or window-close processing. On close, the optional clipboard helper detaches from the terminal, releases history state, destroys the inherited toplevel/surface/buffer objects, and retains only the data-device/source, Wayland connection, immutable snapshot, and any active sends until selection replacement or compositor disconnect. Open stages into a separately growing mapping and commits the document/path only after a successful read; saves use a same-directory temporary file, fsync, and atomic rename. Proportional TrueType advances and OS/2/hhea metrics are shared across wrapping, indexed visual rows, pointer placement and glyph painting. Long lines currently soft-wrap at available pixel width; automatic vertical caret-follow, wheel navigation and the draggable vertical scrollbar are implemented. With wrapping disabled, a draggable horizontal scrollbar supports track clicks, thumb dragging, horizontal-wheel scrolling and Shift+vertical-wheel scrolling; horizontal edge auto-scroll also follows selection drags.

The single-threaded event loop blocks between events, but its poll set includes the Wayland socket, key-repeat timer, four outgoing clipboard pipes and one incoming clipboard pipe. Clipboard state machines use nonblocking descriptors and bounded chunks; transfers do not perform blocking reads/writes in keyboard dispatch. Wayland messages and ancillary SCM_RIGHTS descriptors are received through recvmsg, and protocol payloads are length-checked before parsing.

## Error behavior

The prototype reports concise errors for a missing XDG_RUNTIME_DIR, an unavailable socket, missing required globals, and protocol/shared-memory setup failure. File-operation failures are shown as OPEN ERR or SAVE ERR in the application header while the path prompt remains available for correction or cancellation. A failed Open, including a file larger than 64 KiB, does not replace the active document or its path. A failed atomic save does not truncate the old destination. A wl_display.error event is fatal; its length-prefixed message is printed only after validating the event bounds and NUL terminator. A display-server disconnection terminates the window session.

## XKB type preserve and consumed modifiers

The text-v1 type parser stores one 32-bit preserve mask beside each exact `map[]` entry. A `preserve[mods] = mods;` statement matches an entry by its left-hand modifier combination. If no matching map entry exists yet, the parser creates the specification's implicit Level1 entry; a later `map[]` statement for the same combination updates that entry rather than creating a duplicate. Preserved masks are checked against the type's declared `modifiers` mask.

For a key/group lookup, NekoEdit retains the full compositor modifier state for keysym selection. Separately, it computes the XKB consumed mask as the type's modifier mask minus the preserve mask for the exact matching entry. The document shortcut dispatcher removes consumed Control and Shift from the shortcut state for that key only. Thus an unpreserved Control mapping can select its alternate symbol without accidentally invoking Ctrl+Z, and an unpreserved Shift mapping does not accidentally extend a selection; matching `preserve[Control]` and `preserve[Shift]` entries keep their modifiers available to shortcuts. Raw physical/compositor state is restored on key release, so a per-key decision cannot leak into the next event.

This is type-map consumed-modifier handling for the current Control/Shift shortcut path, not general XKB action execution. Modifier/group actions remain compositor-owned. Alt and other modifiers are not currently filtered because the implemented shortcut set does not use them.
